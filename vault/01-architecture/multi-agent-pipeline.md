# 멀티에이전트 파이프라인

FactoryNote의 에이전트 구조와 6단계 계획 파이프라인을 정의한다.
정체성·차별점·5대 원칙은 [[project-identity]]를 본다.

## 구조 개요

```
사용자 요청
    │
    ▼
┌─────────────┐
│   Director   │  각 Stage마다 하위 에이전트 생성 · 루프 관리 · 게이트 관리
│   Agent      │
└──────┬───────┘
       │ Stage 진입 시 생성
       ├──────────────────┐
       ▼                  ▼
┌─────────────┐   ┌─────────────┐
│   Design     │◄──│  Feedback   │
│   Agent      │──►│  Agent      │
│              │   │              │
│ 산출물 작성  │   │ 보안·병목·  │
│ 구조 설계    │   │ 구조 문제    │
│ 구현         │   │ 탐지         │
└──────┬───────┘   └─────────────┘
       │ 클린 산출물
       ▼
┌─────────────┐
│  사용자      │  검토 · 수정 · 정정 · 확정
│  Gate        │
└──────┬───────┘
       │ 승인
       ▼
   다음 Stage
```

## 에이전트 역할

### Director Agent (조율자)

각 Stage의 진입점이다. 책임:

- 현재 Stage에 맞춰 **Design Agent**와 **Feedback Agent**를 생성한다.
- Design→Feedback→수정 사이클(**Design↔Feedback 루프**)이 종료될 때까지 조율한다.
- Feedback이 클린 판정을 내리면 산출물을 **사용자 게이트**로 넘긴다.
- 사용자가 수정을 요청하면 Design Agent에게 피드백을 전달한다.
- 사용자가 승인하면 다음 Stage로 진행한다.

> Director 자체는 산출물을 작성하지 않는다. 에이전트 생명주기와 게이트만 관리한다.

### Design Agent (설계자)

Stage별 산출물을 작성하는 주체다. 책임:

- 요청을 이해하고 구조를 설계한다.
- 해당 Stage의 산출물(요구사항 명세, 모듈 구조도 등)을 작성한다.
- Feedback Agent의 지적을 받아 산출물을 수정한다.

### Feedback Agent (검토자)

Design Agent의 산출물을 비판적으로 검토한다. 책임:

- **보안 문제** — 인증·인가 결함, 데이터 노출, 인젝션 벡터 등.
- **병목** — 성능 임계점, 확장성 한계, 과도한 동기화 등.
- **구조 문제** — 순환 의존성, 관심사 혼재, 단일 책임 위반, 과잉 추상화 등.

이슈를 발견하면 Design Agent에게 구체적 피드백과 함께 재설계를 요청한다.
이슈가 없으면 Director에게 **클린 판정**을 보낸다.

## Design↔Feedback 루프

각 Stage 내부에서 Design과 Feedback이 번갈아 동작한다:

```
Design Agent가 산출물 작성
        │
        ▼
Feedback Agent가 검토 ──► 이슈 발견 ──► Design에게 피드백 전달
        │                                    │
        │ 클린                            수정 후 재제출
        │                                    │
        ▼◄───────────────────────────────────┘
   사용자 Gate로 이동
```

이 루프는 사용자 게이트 **이전**에 AI 내부에서 품질을 끌어올린다.
사용자는 Feedback이 통과한 산출물만 검토한다.

## 6단계 파이프라인

| Stage | 단계 | 산출물 | 게이트 원칙 |
| ------ | ------ | ------ | ------ |
| 1 | 요청 이해 | 요구사항 명세 | 원칙 1: 승인된 요구사항 없이 설계 불가 |
| 2 | 정상 동작 시나리오 | 시나리오 명세 | 원칙 1 연장: 시나리오 확정 후 설계 진입 |
| 3 | 모듈 아키텍처 설계 | 모듈 구조도 | 원칙 2: 승인된 설계 없이 구현 계획 불가 |
| 4 | 클래스 수준 구조 설계 | 클래스 명세 | 원칙 2 연장: 클래스 설계 확정 후 구현 계획 |
| 5 | 구현 계획 | 구현 순서·의존성 명세 | 원칙 3: 승인된 계획 없이 코드 불가 |
| 6 | 사용자 최종 검증 | (산출물 없음 — 전체 Plan 총괄 검토) | 원칙 5: 검증 통과 전 반영 불가 |

### Stage별 상세

**Stage 1 — 요청 이해**
사용자의 자연어 요청을 분석해 기능적/비기능적 요구사항으로 분해한다.
범위 경계, 제약 조건, 가정을 명시한다. 사용자가 누락이나 오해를 잡는 첫 검문점이다.

**Stage 2 — 정상 동작 시나리오**
요구사항이 충족될 때 시스템이 어떻게 동작해야 하는지를 시나리오로 묘사한다.
정상 경로(happy path)를 중심으로, 사용자가 "이렇게 동작하는 게 맞다"를 확인한다.

**Stage 3 — 모듈 아키텍처 설계**
시스템을 모듈 단위로 분해하고, 모듈 간 책임과 의존성을 정의한다.
전체 구조의 뼈대를 사용자가 검토한다.

**Stage 4 — 클래스 수준 구조 설계**
모듈 내부를 클래스/인터페이스 수준으로 설계한다.
메서드 시그니처, 상태, 협력 관계를 명세한다.

**Stage 5 — 구현 계획**
설계를 바탕으로 구현 순서, 의존성, 마일스톤을 정한다.
코드를 쓰기 전 사용자가 전체 로드맵을 확정한다. (원칙 3 게이트)

**Stage 6 — 사용자 최종 검증**
산출물을 새로 만들지 않는다. Feedback이 산출물 1-5 간 **총괄 일관성 검사**(요구사항↔시나리오↔설계↔계획 정합)를 하고, 전체 Plan을 사용자에게 제시한다.
사용자가 전체 Plan을 검증·승인하면 파이프라인 완료. (원칙 5 게이트)

## 인간 승인 게이트

각 Stage는 **사용자 게이트**로 끝난다. 사용자는 세 가지 행동을 할 수 있다:

- **확정** — 산출물을 승인하고 다음 Stage로 진행.
- **수정** — 직접 편집하거나 Design Agent에게 수정 지시.
- **정정** — 방향 자체가 틀렸다고 판단하면 이전 Stage로 회귀.

> 게이트는 "다음으로 넘어가도 되는가"를 사용자가 결정하는 유일한 검문점이다.
> AI(Feedback Agent 포함)는 게이트를 통과시킬 수 없다.

## 확장성

현재 3개 에이전트(Director, Design, Feedback)가 전체 역할이다.
그러나 설계는 확장을 전제로 한다:

- **단계별 에이전트 변형** — 특정 Stage에 특화된 에이전트를 투입할 수 있다.
  예: Stage 3(모듈 설계)에 전용 아키텍처 검토 에이전트, Stage 6(최종 검증)에 전용 일관성 검토 에이전트.
- **역할 추가** — 문서화 에이전트, 성능 분석 에이전트 등 새 역할을 Director 하위에 추가할 수 있다.
- **harness 적응** — Pi/Codex/Claude Code 각 환경의 에이전트 스폰 방식에 맞춰 구현체만 교체한다.

> 에이전트 추가 시 이 문서의 "에이전트 역할" 절과 [[project-identity]] 용어집을 함께 갱신한다.
