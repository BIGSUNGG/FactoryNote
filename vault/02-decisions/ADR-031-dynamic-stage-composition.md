# ADR-031: 고정 3단계를 대체하는 디렉터 동적 스테이지 구성

> **TL;DR**: 파이프라인 단계를 고정 3단계에서 **카탈로그(6종) 기반 동적 구성**으로 전환한다. 디렉터(Tier 1 에이전트)가 피처 시작 시 종류·개수·순서를 매번 새로 결정하고, 구성 승인 게이트는 없다(디렉터 전권). 사용자는 `/factorynote stage <n>` 으로 최대 스테이지 개수를 제한한다. 각 구성 단계는 기존과 동일하게 산출물 + 사용자 게이트 + Design↔Feedback 루프를 가진다. [[ADR-008-3-stage-pipeline]] 의 카디널리티 결정을 대체한다.

## 상태

accepted. [[ADR-008-3-stage-pipeline]](6단계 → 3단계 통합)의 *고정 카디널리티* 전제를 본 ADR이 대체한다 — ADR-008의 통합 판단(게이트 과다 해소, Stage 6 폐지)은 그대로 유효하며, 본 ADR은 단계 구성을 '고정 3'에서 '디렉터 선택 N'으로 바꾼다.

## 날짜

2026-08-18

## 맥락 (Context)

ADR-008 로 고정된 3단계(요청 이해·시나리오 → 모듈·클래스 설계 → 구현 계획)는 모든 기능 요청에 동일한 파이프라인을 강제한다. 실사용에서 두 가지 비효율이 드러났다.

1. **단순 요청 과다** — 작은 변경에도 3단계 전체(그래프 설계 포함)를 거쳐야 한다.
2. **복잡 요청 부족** — 리스크·테스트·비기능 검증을 계획에 담을 단계가 없다.

## 결정 (Decision)

### 1. 스테이지 카탈로그 6종

| kind | 단계 | 산출물 | 그래프 |
| --- | --- | --- | --- |
| `understanding` | 요청 이해 · 동작 시나리오 | 요구사항·시나리오 명세 | none |
| `design` | 모듈 · 클래스 설계 | 설계(모듈·클래스) | required |
| `implementation` | 구현 계획 | 구현 순서·의존성 명세 | optional |
| `risk-analysis` | 리스크 분석 | 리스크·완화 명세 | none |
| `test-strategy` | 테스트 전략 | 테스트 전략 명세 | none |
| `nfr` | 비기능 요구 검증 | NFR 목표·검증 명세 | none |

- 기존 3종은 designPrompt·산출물 파일명(`01-understanding-and-scenarios.md` 등) 그대로 유지 — 레거시 피처와 파일 호환.

### 2. 동적 구성(디렉터 전권)

- 디렉터(Tier 1, `factorynote_plan` 구동 에이전트)가 첫 호출에서 카탈로그 kind 순서 목록(`stages` 파라미터)을 제출한다. 같은 종류 반복 허용.
- 첫 호출에 구성이 없으면 도구는 `nextAction=compose` 로 카탈로그 메뉴 + 판단 기준을 돌려준다. **구성 자체에 대한 승인 게이트는 없다** — 사용자 통제점은 각 단계 산출물 게이트(기존 5대 원칙 유지).
- 구성은 생성 시 `state.json` 에 영속화되고 이후 불변(회귀는 구성 내 위치 기준으로만).

### 3. 최대 스테이지 개수 제한

- `/factorynote stage <n>` (또는 `stage off`) — 세션 상한. 새 파이프라인 생성 시 적용하고 `state.maxStages` 에 영속화. 진행 중 재실행 시 state 갱신.
- 상한 초과 구성은 **앞에서부터 잘라서 적용**(truncate)하고 메시지로 통지. 도구 파라미터 `maxStages` 가 세션 값보다 우선.

### 4. 상태 모델

- `PipelineState.stages: StageKind[]` 추가. `stage`·`validThrough` 는 구성 내 위치(1부터). 구 state(`stages` 없음)는 레거시 3종 구성으로 마이그레이션, 미등록 종류 포함 state 는 손상 복구 경로.
- 산출물 파일명 = `<위치 2자리>-<종류 접미부>.md` — 위치 접두로 종류 반복 시에도 유일, 단계 폴더(`stageN/`)도 파일명에서 직접 추론(구성 독립).

## 이유 (Rationale)

- 구성 승인 게이트를 두지 않은 것은 사용자 결정 — 게이트 수를 늘리지 않으면서도 각 산출물 게이트가 실질 통제를 유지한다.
- 잘라내기(truncate)는 '제한되어 적용'이라는 직관적 상한 의미와 단순성(재호출 왕복 없음)의 절충.
- Feedback 검토 축 레지스트리(ADR-014)의 단계 필터(1|2|3)는 유지하고, 새 종류는 가장 가까운 프로필로 사상(`feedbackProfileOf`) — 레지스트리 32개 항목 무변경. 메뉴는 어차피 Director 가 상황에서 추려 쓴다.

## 대안 (Alternatives)

- **구성 승인 게이트 추가** — '스테이지 0' 게이트로 구성을 사용자 승인. 사용자 결정으로 기각(디렉터 전권).
- **상한 초과 시 거부·재제출** — 더 정확하나 왕복 비용. 기각.
- **Feedback 에이전트 stages 필드를 종류로 전면 개편** — 32개 항목 재분류 필요. 프로필 사상으로 대체.

## 결과 (Consequences)

- 긍정: 요청 복잡도에 맞는 파이프라인(단순 축소·복잡 확장), 새 검토 축(리스크·테스트·NFR) 계획 반영, 사용자 상한 통제.
- 부정/트레이드오프: 구성 편차(매번 새로 구성 — 사용자 선택), 상한 잘라내기 시 뒷부분 종류 손실 가능(메시지 통지).
- 자체체크 236건 green(구성 길이 2·4·5단계 전이, 상한 clamp·영속, 레거시 마이그레이션, 카탈로그 불변식 포함).
