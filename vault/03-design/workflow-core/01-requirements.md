# Workflow Core 요구사항 명세

FactoryNote 6단계 파이프라인의 **실행 코어**에 대한 요청 이해 산출물(Stage 1).
정체성·아키텍처 배경은 [[project-identity]], [[multi-agent-pipeline]]을 본다.

## 개요

Workflow Core는 FactoryNote의 6단계 계획 파이프라인을 구동하는 실행기다.
**Hybrid 모델**([[ADR]] 예정): 마크다운 프로토콜(단계 정의·게이트 로직·루프 규칙)이 실행 본체이고,
얇은 상태기계가 영속/resume를 담당한다.

> 핵심 제약: FactoryNote는 "harness에 설치하는 패키지" + "harness-agnostic"이므로,
> 코어가 LLM API를 직접 호출하지 않는다. 에이전트 스폰은 `AgentSpawn` 인터페이스에 의존하며,
> **어떤 harness 확장도 없으면 Tier 0(역할 전환)로 축소 동작**한다. 자세한 건 아래 "에이전트 스폰 티어" 참조.

## 에이전트 스폰 티어

코어는 항상 6단계+게이트를 보장한다. 에이전트 분리 정도만 환경에 따라 달라진다:

| 티어 | 조건 | 동작 |
| ---- | ---- | ---- |
| **Tier 0** | 항상 (어떤 harness든, 확장 없이) | 단일 에이전트가 Director·Design·Feedback **역할을 인라인 전환**. pi-crew 불필요. |
| **Tier 1** | 서브에이전트 시스템 있을 때 | 어댑터가 Design/Feedback을 **분리된 에이전트**로 스폰. 진짜 격리·독립 컨텍스트. Pi에서는 pi-crew로 켬. |

> pi-crew는 **강화**(격리/신뢰 up)이지 요구사항이 아니다. 없으면 Tier 0로 6단계 게이트가 그대로 동작한다.

## 기능적 요구사항

| ID   | 요구사항                                                                                                                                                        |
| ---- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| FR-1 | **6단계 순차 구동** — 정의된 순서(요청이해→시나리오→모듈설계→클래스설계→구현계획→검증)로 단계 진행. 한 단계는 이전 단계 게이트 승인 후에만 진입한다.                                                                   |
| FR-2 | **단계별 Design↔Feedback 루프** — 각 단계에서 Design 에이전트가 산출물 작성, Feedback 에이전트가 검토. 클린 판정까지 반복. **반복 상한**(기본 3회, 사용자 조정 가능) 도달 시 **미해결 이슈 목록과 함께** 사용자 게이트로 에스컬레이션. |
| FR-3 | **인간 게이트** — Feedback 클린(또는 상한 도달) 시 산출물을 사용자에게 제시. 세 가지 판정 대기: **승인**(다음 단계) / **수정**(사용자 직접 편집 또는 Design에게 수정 지시) / **정정**(이전 단계 회귀).                     |
| FR-4 | **산출물 영속화** — 승인된 단계 산출물을 `<outputDir>/<feature>/<NN-stage>.md`로 저장(기본 `designs/`, 설정 가능; vault 의존 X; Doc-Conventions 준수).                                  |
| FR-5 | **파이프라인 상태 영속화** — 현재 단계, 게이트 상태, 루프 반복수, 회귀 이력을 상태 파일(`.factorynote/state.json`, 리포 루트·gitignore)에 저장. 세션 경계를 넘어 resume 가능.                                |
| FR-6 | **에이전트 스폰(`AgentSpawn` 인터페이스)** — Director(조율 세션)가 단계마다 Design·Feedback을 스폰·결과 수집·수거. Pi 어댑터는 pi-crew 사용, 다른 harness는 자기 수단. **어댑터 없으면 Tier 0(역할 전환)로 축소.** |
| FR-7 | **회귀 지원** — 사용자 "정정" 시 **여러 단계 점프 회귀 허용**. 대상 단계 이후 산출물/상태 자동 무효화.                                                                                          |
| FR-8 | **파이프라인 시작 트리거** — Pi 명령 `/factorynote <feature>` 로 새 파이프라인 시작.                                                                                             |

## 비기능적 요구사항

| ID    | 요구사항                                                                                                                                      |
| ----- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| NFR-1 | **harness-agnostic 프로토콜** — 단계 정의·게이트·루프 규칙은 harness 중립(마크다운/스키마). 에이전트 스폰은 `AgentSpawn` 인터페이스; Pi 어댑터(pi-crew, Tier 1)만 우선 구현, Codex/Claude Code 어댑터는 코어 수정 없이 추가 가능. Tier 0는 어댑터 없이 항상 동작. |
| NFR-2 | **상태 신뢰성** — 상태 파일 쓰기는 atomic(write-then-rename). 로드 시 손상/부분 기록 감지 및 복구. 게이트 판정은 에이전트 기억이 아닌 **상태 파일이 권위**.                               |
| NFR-3 | **투명성/감사** — 루프 반복 이유, Feedback 발견 항목, 게이트 판정을 모두 기록에 남겨 설계 추적 가능.                                                                        |
| NFR-4 | **낮은 복잡도** — 얇은 코드, 프로토콜이 본체. Director 1개, 온디맨드 스폰, 추측성 에이전트 타입 금지(ponytail).                                                             |
| NFR-5 | **컨벤션 준수** — 산출물은 Doc-Conventions; 상태 파일 위치/형식도 문서화.                                                                                      |
| NFR-6 | **서브에이전트 장애 처리** — Design/Feedback 서브에이전트 실패·크래시 시 재시도 또는 사용자 알림(무한 대기/조용한 실패 방지).                                                        |
| NFR-7 | **우아한 축소(Tier 0)** — pi-crew 등 서브에이전트 시스템이 없는 환경에서도 단일 에이전트 역할 전환으로 6단계+게이트가 동작해야 한다. 코어는 pi-crew에 하드 의존하지 않는다. |

## 범위

**IN (이번 설계 대상)**

- 6단계 구동, Design↔Feedback 루프(상한 포함), 인간 게이트
- 산출물 + 상태 영속화, resume
- Pi 어댑터(pi-crew, Tier 1) + Tier 0(역할 전환) 기본
- 상태 스키마
- 산출물은 설정 가능한 `<outputDir>`(기본 `designs/`)에 저장. Changelog/Dev-Log 갱신은 사용자가 doc-workflow대로 수동 — 코어가 자동 갱신하지 않는다.

**OUT (지금 제외)**

- Codex/Claude Code 어댑터 구현(인터페이스만 남김)
- 웹 UI / 독립 CLI 앱
- 다중 파이프라인 동시 실행(MVP는 한 번에 한 feature)
- 실제 코드 구현(Stage 5 구현계획 이후 별도)

## 제약

- 6단계+게이트는 어떤 harness든 동작(Tier 0). 분리 에이전트(Tier 1)는 Pi 어댑터(pi-crew)로 우선 구현.
- 산출물은 `<outputDir>/<feature>/` 마크다운.
- 기존 `AGENTS.md` + `.pi/skills/doc-workflow` 하이브리드와 공존.
- 파이프라인 상태는 `.factorynote/state.json`(리포 루트, gitignore)에 저장. vault 안에 두지 않는다(ADR-001: vault=문서 진실, 상태는 런타임). Pi 세션(휘발성) 경계를 넘어 살아야 한다.

## 가정

- 파이프라인 인스턴스 1개 = 1개 feature 설계(예: "workflow-core").
- 사용자는 인터랙티브 Pi 세션에서 게이트에 응답한다.
- Design·Feedback은 Tier 1에서 fresh-context 서브에이전트로 스폰; Tier 0에서는 단일 에이전트의 인라인 역할 전환.
- 산출물은 `<outputDir>/<feature>/`에 누적되며 그 feature의 진실의 원천이다.

## 게이트 결정 사항 (승인됨 2026-07-28)

1. **상태 파일 위치** → `.factorynote/state.json`(리포 루트, gitignore). vault 안에 두지 않음(ADR-001).
2. **Feedback 반복 상한** → 기본 3회, 사용자 조정 가능. 상한 도달 시 미해결 이슈 목록과 함께 게이트로 에스컬레이션.
3. **회귀 범위** → 여러 단계 점프 회귀 허용 + 대상 단계 이후 산출물/상태 자동 무효화.
4. **문서 동기화** → 산출물만 생성. Changelog/Dev-Log 갱신은 사용자가 doc-workflow대로 수동(코어 자동 갱신 X).
5. **시작 트리거** → Pi 명령 `/factorynote <feature>`.

## Feedback 패스 결과 (Design↔Feedback 루프)

Feedback이 초안에서 잡아 Design이 반영한 항목:

- **구조**: Director가 "별도 프로세스"인지 "조율 역할"인지 모호 → 가정에 "Director=조율 세션, Design/Feedback=스폰 서브에이전트" 명시.
- **누락**: 파이프라인 시작 진입점 없었음 → **FR-8**(시작 트리거) 추가.
- **병목**: Design↔Feedback 무한 루프 가능 → **FR-2에 반복 상한**(기본 3회) + 상한 도달 시 게이트 에스컬레이션 명시.
- **신뢰성**: 서브에이전트 크래시 시 무한 대기/조용한 실패 → **NFR-6**(장애 처리) 추가; **NFR-2**에 "게이트 판정은 상태 파일이 권위" 강화.
- **구조(게이트에서 포착, 2차 Feedback)**: FR-6/NFR-1이 pi-crew에 과결합 → **Tier 0/1 모델** 도입, `AgentSpawn` 인터페이스화, **NFR-7**(우아한 축소) 추가. pi-crew를 요구사항→강화로 강등.
